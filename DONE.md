## Data quality score (2026-11-16)

Added 2026-11-16. Replaces the "Data tier" field (Raw / Clean), whose values did not tell users what to expect. The new score tells them how much preparation a dataset version needs before it can be used: a fixed list of yes/no criteria, shown as a count (e.g. `3/7`). Do the three parts below in order; they can be one change.

**The criteria** (in this order; the texts are final, copy them as they are):

| Key | Short label | Question for the editor | If "no", the user has to… |
|---|---|---|---|
| `in_one_piece` | In one piece | Is all the released data of this kind in one table, with no batches, cohorts or files to stack? | Find the other pieces and align them before stacking |
| `keyed_by_finngenid` | Keyed by FINNGENID | Does every row carry a FINNGENID? | Map sample or other IDs first, and lose the rows that don't map |
| `only_useful_columns` | Only useful columns | Is every column populated and meant for analysis (no empty, duplicated or debug columns)? | Work out which columns to drop |
| `consistent_values` | Consistent values | Is the same thing always recorded the same way across sources, batches and years: one unit and scale per measurement, one coding system per column, no free text to parse? | Harmonise units, scales and codes, or extract values from text |
| `quality_checked` | Quality-checked | Have known errors, duplicates and contradictions been removed or flagged in the data itself? | Run their own QC and deduplication |
| `documented` | Documented | Is there a description, in English and linked from this entry, of every column, its codes, and what one row represents? | Reverse-engineer the data or ask the data owner |
| `readable_without_codebook` | Readable without a codebook | Can the values be read as they are: plain labels or a standard vocabulary (ICD-10, ATC, OMOP…), with missing values left empty and not given a code? | Translate values from a codebook before the data can be read or summarised |

**Rules that hold for all three parts:**

- **One list, defined once.** Put the criteria in one module (e.g. `FGDataCatalog.Catalog.DataQuality`): an ordered list of `%{key, label, question, if_no}`. The form, the modal, the score and the validation all read this list. Criteria will be added and removed over time by editing it; nothing else should need to change, and no migration.
- **All versions are scored against the current list.** There is no per-version or historical criteria set.
- **Answers:** each criterion is Yes, No or Unknown per dataset version. Unknown is the default.
- **Score:** the number of current criteria answered Yes, over the number of current criteria. Unknown counts the same as No. A version with nothing answered shows `0/7`.
- **Storage:** one map column on `dataset_versions` (e.g. `data_quality`, `:map`, default `%{}`), keyed by criterion key, with values `"yes"` or `"no"`. Unknown is an absent key. So a newly added criterion is Unknown everywhere, and the answers of a removed criterion are ignored (stored keys not in the current list never count, and are never shown). Never reuse the key of a removed criterion for a different question.
- **Casting:** keep only keys of the current list and the values `"yes"` / `"no"`; drop everything else (`"unknown"`, `""`, unknown keys). Compare keys as strings: no `String.to_atom/1` on params.

## Version states and editors (2026-11-16)

Decided and done 2026-11-16. Replaces the admin / editor split and the `status` + `archived_at` pair with one state per dataset version and one rule table. Goal: a simpler system that gives signed-in users more responsibility, with no review step.

**The rules** (final):

| State \ Actor | Logged-out user | Non-owning editor (signed in) | Owning editor (signed in) |
|---|---|---|---|
| Published | read | read, write, unpublish (→ Draft), archive | read, write, unpublish (→ Draft), archive |
| Draft | hidden | read, archive | read, write, publish (→ Published), archive |
| Archived | hidden | read, unarchive (→ Draft) | read, unarchive (→ Draft) |

- Every signed-in user is an editor. There is no admin any more.
- Every editor may create a dataset or a new version of any dataset, including a dataset whose versions are all archived. A new dataset or version starts as a Draft, and the editor who creates it becomes its owning editor.
- Whoever moves a version into Draft (create, unpublish, unarchive) becomes its owning editor. This is also how an editor takes over someone else's draft (archive it, then unarchive it) and how versions with no owner (seeds, older data) get one. There is no separate "take ownership" action.
- The owning editor only matters in Draft: in Published and Archived, all editors have the same rights.
- "Write" covers every way of editing: the edit page, quick edit in the catalog, and the dataset's name and description (see part 4).
- Every editor may see the changelog and revert any change set. Accepted consequence: a revert writes columns back directly (state, owner, fields), so it can undo any transition or a draft owner's edits. The changelog records who did it.
- Every editor sees every Draft in the catalog. A Draft sorts among the dataset's versions by release date as today, so a newer Draft by anyone becomes the dataset's top row for every signed-in user. Logged-out users see Published versions only.
